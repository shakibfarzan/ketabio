# Multilingual dynamic content in Ketabio

Ketabio is bilingual (English + Persian). Two different mechanisms handle two different kinds of
text:

| Kind of text                      | Examples                                               | Mechanism                              |
| --------------------------------- | ------------------------------------------------------ | -------------------------------------- |
| **Static UI copy**                | buttons, labels, validation messages, errors           | `next-intl` + `messages/{locale}.json` |
| **Dynamic content** (from the DB) | book titles/descriptions, author names, category names | `*_translations` tables                |

`next-intl` never reads the database, and the database never stores UI strings.

---

## 1. Why translation tables (and not `title_en` / `title_fa` columns)

The original schema stored `books.title` and `books.description` as single columns, so a book
could only exist in one language. Adding a language would have meant an `ALTER TABLE` per entity
per language, and every query would have had to know the column suffix.

With a translation table:

- **Adding a language is data, not schema.** A new locale is one value in the `locale` enum; no
  column changes, no query changes.
- **Entities are not duplicated.** `books.slug`, `books.cover_image`, `books.page_count` exist
  once, so `en` and `fa` readers land on the same canonical record.
- **Relations stay language-independent.** `book_categories`, `books.author_id` and (in future)
  a category `parent_id` are shared by every language — the taxonomy cannot diverge per locale.
- **Missing translations degrade gracefully** instead of showing an empty string (see
  [fallback](#5-how-fallback-works)).

## 2. What belongs where

```text
ENTITY                          language-independent
  books        id, slug, cover_image, language, page_count, published_at, author_id, isbn, created_at
  authors      id, slug, avatar_url, created_at
  categories   id, slug, created_at

TRANSLATION                     language-dependent, one row per (entity, locale)
  book_translations       id, book_id,     locale, title, description, created_at
  author_translations     id, author_id,   locale, name,  bio,         created_at
  category_translations   id, category_id, locale, name,               created_at
```

Rules of thumb:

- **Slugs stay on the entity.** They are canonical URLs, shared by all locales
  (`books.slug = 'the-little-prince'` for both `The Little Prince` and `شازده کوچولو`).
- **Dates, numbers, files, FKs and IDs stay on the entity.**
- **Anything a human reads stays in the translation table.**
- **`books.language` stays on `books`** — it records the language the work was _written_ in
  (metadata), not a translation of anything.
- If categories ever gain a hierarchy, `parent_id` goes on `categories`, never on
  `category_translations`. (Categories are flat today, so the column does not exist yet.)

Constraints on every translation table:

- `UNIQUE (<entity>_id, locale)` — one translation per language, enforced by the database.
- `ON DELETE CASCADE` on the entity FK — deleting a book removes its translations.
- Indexes on `<entity>_id` and `locale`.
- `category_translations` additionally keeps `UNIQUE (locale, name)`, which preserves the old
  `categories_name_unique` rule now that the name lives in the translation table.

## 3. Where locales are defined

`constants/locales.ts` is the single source of truth:

```ts
export const LOCALES = ['en', 'fa'] as const;
export type Locale = (typeof LOCALES)[number];
export const DEFAULT_LOCALE: Locale = 'en'; // unknown/missing cookie
export const FALLBACK_LOCALE: Locale = 'en'; // content with no translation for the locale
export const LOCALE_COOKIE = 'locale';
```

Everything derives from it:

- `db/schema.ts` → `localeEnum = pgEnum('locale', LOCALES)`
- `lib/request-locale.ts` → reads/validates the cookie
- `lib/validators/book.schema.ts` → one Zod object per locale
- `app/admin/books/_components/book-form.tsx` → one input block per locale
- `components/navbar/switch-locale.tsx` → one menu entry per locale

Do not hard-code `'en'` / `'fa'` in new code — import from `constants/locales.ts`.

## 4. How locale selection works

```text
cookie `locale`  →  lib/request-locale.ts::getRequestLocale()  →  Locale
                                   │
              ┌────────────────────┴────────────────────┐
              ▼                                         ▼
   i18n/request.ts (next-intl)              Server Component / Server Action
   messages/{locale}.json                   passes `locale` to db/* queries
```

`getRequestLocale()` is the only place that reads the cookie for data purposes. It validates the
value and falls back to `DEFAULT_LOCALE`, so an arbitrary cookie value can never reach SQL.

**`db/*` never reads the request.** Callers resolve the locale and pass it down explicitly:

```ts
// app/admin/books/edit/[slug]/page.tsx
const locale = await getRequestLocale();
const book = await getBookBySlug(slug, locale);
```

This keeps the repository testable and free of `next/headers`.

## 5. How fallback works

```text
requested locale  →  translation exists?  ──yes──▶  use it
                              │
                              no
                              ▼
                    FALLBACK_LOCALE ('en')  →  use it
```

Two tiers, nothing more. In SQL (`db/translation-sql.ts`) the translation table is joined twice
and collapsed with `COALESCE`:

```ts
.leftJoin(t,   and(eq(t.bookId, books.id),   eq(t.locale, locale)))
.leftJoin(tf,  and(eq(tf.bookId, books.id),  eq(tf.locale, FALLBACK_LOCALE)))
// select
title: sql`coalesce(${t.title}, ${tf.title})`
```

`LocalizedBook.locale` reports which of the two was used (`'fa'`, `'en'`, or `null` when a row
has no translation at all), so the UI can flag untranslated content.

Each entity falls back **independently**: a book whose Persian translation was deleted still
shows its Persian author's name, because `author_translations` has a `fa` row.

To guarantee tier 2 always resolves, the fallback locale is **required** on create
(`lib/validators/book.schema.ts`): a book must have an English title, other languages are
optional. In memory the same order lives in `lib/localization.ts::resolveTranslation`.

## 6. How to query localized data

Use the repository — it returns already-localized, flat objects:

```ts
import { listBooks, paginateBooks, searchBooks, getBookBySlug } from '@/db/books';
import { listAuthors } from '@/db/authors';
import { listCategories } from '@/db/categories';
import { getRequestLocale } from '@/lib/request-locale';

const locale = await getRequestLocale();

const { items, total, page, totalPages } = await paginateBooks(locale, {
  search: 'شازده',
  page: 1,
  pageSize: 20,
});

items[0].title; // 'شازده کوچولو'  (or the English title, if fa is missing)
items[0].description; // localized
items[0].author?.name; // localized
items[0].categories[0].name; // localized
items[0].locale; // which locale was used
```

Available reads:

| Function                                                  | Returns                                                         |
| --------------------------------------------------------- | --------------------------------------------------------------- |
| `listBooks(locale, options?)`                             | `LocalizedBook[]`                                               |
| `paginateBooks(locale, options?)`                         | `BookPage` (`items`, `total`, `page`, `pageSize`, `totalPages`) |
| `searchBooks(term, locale, options?)`                     | `BookPage`                                                      |
| `getBookById(id, locale)` / `getBookBySlug(slug, locale)` | `LocalizedBook` (throws `BOOK_NOT_FOUND`)                       |
| `getBookTranslations(bookId)`                             | `BookTranslation[]` (all locales, unresolved — edit forms only) |
| `listAuthors(locale)` / `getAuthorById(id, locale)`       | `LocalizedAuthor`                                               |
| `listCategories(locale)` / `getCategoryById(id, locale)`  | `LocalizedCategory` (cached per locale)                         |
| `listCategoriesForAdmin(locale)`                          | `LocalizedCategory & { translations }`                          |

**Do not** resolve translations in components. There is no `book.translations.find(...)` in the
UI; if you need a new localized field, add it to the query's `select` list.

### Writing

```ts
await createBook({
  translations: {
    en: { title: 'The Little Prince', description: 'A novella' },
    fa: { title: 'شازده کوچولو', description: '…' },
  },
  language: 'French',
  authorId,
  categoriesIds: [categoryId],
  bookFiles: [{ format: 'pdf', fileUrl }],
});
```

`createBook` / `updateBook` / `createCategory` / `updateCategory` write the entity and its
translations in **one `db.batch()`** — the atomic primitive of the `neon-http` driver — so a
partial write (book without translations) is impossible. Book ids are generated with
`randomUUID()` so the dependent rows can join the same batch. Translation updates are upserts
keyed on `(book_id, locale)`, so editing never creates duplicate rows.

### Searching

`searchBooks` / `paginateBooks({ search })` match `book_translations.title` and `.description`
with `ILIKE`, restricted to the requested locale plus the fallback locale, so a Persian query
finds Persian titles and an English query finds English ones. Wildcards in user input are escaped
(`escapeLikePattern`).

## 7. How to add another language

1. `constants/locales.ts` — append the code to `LOCALES`, e.g. `['en', 'fa', 'ar'] as const`.
2. Add `messages/ar.json` (static UI copy) and the `Locales.ar` label to every message file.
3. Add `RTL_LOCALES` / a flag entry in `components/navbar/switch-locale.tsx` if needed.
4. `npm run migrate` — regenerates the `locale` enum.
5. Add translations for existing content (`INSERT INTO book_translations …`), or let the fallback
   show English until they exist.

That is all. The Zod schemas, the admin form blocks, the queries and the SQL joins are all driven
by `LOCALES`, so they pick the new language up automatically.

---

## 8. Extending to new entities

For a `Publisher`, `Series` or `Genre`:

1. Keep language-independent columns on the entity, plus a canonical `slug`.
2. Add `<entity>_translations` with `id`, `<entity>_id` (`ON DELETE CASCADE`), `locale`,
   the translated columns, `UNIQUE (<entity>_id, locale)` and indexes on `<entity>_id`/`locale`.
3. Add Drizzle `relations()` on both sides.
4. Add a `Localized<Entity>` type and a query that joins the translation table twice and
   `COALESCE`s (copy `db/categories/queries.ts` — it is the smallest example).
5. Add the Zod translations object and the form block.

A generic polymorphic translation table was deliberately **not** used: explicit per-entity tables
keep foreign keys, indexes and types precise.

## 9. Tests

`npm test` runs (among others):

- `tests/i18n/migrations.test.ts` — replays the real SQL migrations against a legacy database and
  checks that data is moved into the translation tables without loss.
- `tests/i18n/seed.test.ts` — seeds and verifies localized reads, fallback and search.
- `tests/errors/books.repository.test.ts` — multi-locale writes, the unique `(book_id, locale)`
  constraint, cascade deletes, atomic rollback, per-locale search and pagination.
- `tests/errors/books.actions.test.ts` — per-locale validation field codes on the server actions.
